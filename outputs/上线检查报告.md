# 家政清洁服务小程序 · 上线检查报告

| 项目 | 内容 |
| --- | --- |
| 检查日期 | 2026-10-05 |
| 检查范围 | 代码实现、配置安全、合规材料、运维保障 |
| 总体结论 | **暂不满足上线条件**，存在 8 项阻塞问题 |

---

## 一、总体结论

功能闭环已经完整（用户下单支付 → 派单 → 保洁师履约 → 用户确认 → 评价），但**"能跑通"和"能对外营业"是两件事**。目前主要缺口集中在三块：

1. **交易未真实打通**：支付走的是模拟通道，真实的微信支付下单、回调验签、退款打款都没实现。
2. **身份与密钥是开发态**：保洁师和管理员用固定登录码进入，密钥和密码都是开发默认值，任何人拿到地址就能登录后台。
3. **合规材料缺失**：隐私政策、用户协议、类目资质都没有，小程序审核这一关过不去。

---

## 二、阻塞项（不解决不能上线）

### P0-1 真实微信支付未接入

**现状**：`apps/api/src/modules/payment/providers/wechat.provider.ts` 里所有方法都是直接抛异常，只有 Mock 通道可用；支付回调接口 `POST /payments/notify` 在非模拟模式下会拒绝处理（这是有意为之，避免未验签的回调影响订单）。

**风险**：无法真实收款，退款也只是数据库记录，没有资金流动。

**要做**：
- 申请微信支付商户号，配置 `.env` 里的 `WXPAY_MCHID`、`WXPAY_SERIAL_NO`、`WXPAY_PRIVATE_KEY`、`WXPAY_API_V3_KEY`、`WXPAY_NOTIFY_URL`
- 实现 JSAPI 统一下单、回调验签解密、申请退款三个接口
- 把 `WX_MOCK` 置为 `false`

### P0-2 小程序仍是游客态

**现状**：`apps/miniprogram/project.config.json` 里 `appid` 是 `touristappid`（开发者工具的测试号）。

**要做**：注册正式小程序账号 → 选择"生活服务/家政"类目并提交资质 → 拿到正式 AppID → 填入项目配置和 `.env` 的 `WX_APPID`/`WX_SECRET`。

### P0-3 保洁师与后台管理员是"固定登录码"

**现状**：保洁师用 `staff_dev001` 这类登录码进入，后台用 `admin / admin123`。这两个入口**没有任何真实身份校验**，知道规则的人都能进。

**风险**：这是当前最严重的安全问题——外部人员可以登录保洁师端看客户地址电话，或登录后台看到全部订单数据。

**要做**：
- 保洁师端改为微信授权登录 + 平台审核开通（`StaffService.login` 已经按 openid 匹配，只需要把 openid 的来源从"登录码"换成真实 `wx.login`）
- 后台加登录失败次数限制、强密码策略；正式环境必须修改默认密码

### P0-4 密钥与密码仍是开发默认值

**现状**（`apps/api/.env`）：

```
DATABASE_URL="mysql://root:root123456@localhost:3306/home_cleaning"
JWT_SECRET="dev-only-secret-please-change-in-production"
```

**风险**：JWT 密钥泄露意味着任何人都能伪造任意用户的登录令牌。数据库密码同样是弱口令。

**要做**：上线前换成强随机值，并把密钥从代码库移出（用环境变量或密钥管理服务注入）。

### P0-5 上传的服务照片公开可访问

**现状**：`main.ts` 里用 `useStaticAssets` 把 `uploads` 目录挂成了公开静态目录，任何人只要知道 URL（`/uploads/2026/10/xxx.jpg`）就能直接打开。

**风险**：打卡照片和完工照片**包含用户家里的内景**，这是隐私泄露，也违反个人信息保护的相关要求。

**要做**：改为鉴权访问（例如经过后端签名校验后再返回文件，或改用对象存储的私有读 + 临时签名 URL）。当前实现只是为了开发期方便，代码里已标注。

### P0-6 隐私政策、用户协议等页面缺失

**现状**：小程序里没有任何法律文本页面。微信小程序审核强制要求隐私政策，且要求与实际收集的信息一致（本项目收集了手机号、位置、相册）。

**要做**：准备并上线 4 份文本：隐私政策、用户协议、服务条款、取消与赔付规则；在"我的"里加入口；在微信公众平台填写《用户隐私保护指引》。

### P0-7 手机号明文存储

**现状**：用户手机号（`user.phone`）、地址联系人手机号（`address.contactPhone`）都是明文入库，代码里留了 TODO 但未实现。

**风险**：数据库一旦泄露，用户手机号直接暴露；也不符合"敏感个人信息加密存储"的要求。

**要做**：接入 AES 加密存储（字段级加密），并确保日志中不出现明文手机号。

### P0-8 小程序接口地址指向 localhost

**现状**：`apps/miniprogram/config/index.js` 里 `BASE_URL` 是 `http://localhost:3000/api/v1`，且微信开发者工具勾选了"不校验合法域名"。

**要做**：部署到有 ICP 备案的域名（HTTPS），改掉配置，并在小程序后台配置 request 合法域名。

## 六、灰度与回滚方案

**灰度节奏**

| 阶段 | 范围 | 放量上限 | 观察期 |
| --- | --- | --- | --- |
| 内测 | 员工 + 亲友 | 不限制 | 3–5 天 |
| 单区灰度 | 1 个行政区 | 20 单/日 | 1 周 |
| 扩区 | 2–3 个行政区 | 50 单/日 | 2 周 |
| 全量 | 全城 | 不限制 | — |

**回滚触发条件**

- 支付成功率连续 2 小时低于 80%
- 出现资金差异（金额不符、重复扣款）
- 库存超卖（同一时段被重复售卖）
- 大面积无法下单或无法派单

**回滚手段**

- 后端：镜像回滚到上一版本（需要保留上一版镜像）
- 小程序：后端接口必须同时兼容"线上版本 + 待审版本"
- 数据：数据库变更采用"先加字段、再发代码、最后清理"的三步走，避免回滚时字段不兼容
- 兜底：极端情况下暂停下单入口，改用客服人工接单

## 七、值班与应急

| 场景 | 处理方式 | 责任人 |
| --- | --- | --- |
| 无人接单 | 后台人工派单；仍无人则联系用户改期或全额退款 | 运营 |
| 保洁师爽约 | 立即改派 + 补偿用户 | 客服 |
| 用户投诉损坏 | 24 小时内定损，走保险或责任赔付 | 客服 + 运营 |
| 支付异常 | 核对支付流水，必要时手动退款 | 技术 + 财务 |
| 系统故障 | 按回滚流程处理，同步告知用户 | 技术 |
